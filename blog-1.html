    Ship on Fridays: designing a CI/CD pipeline you can trust

    Lumora Engineering•14 March, 2025•8 min read
    ← All articles
    On this page

      Most teams that avoid Friday deploys will tell you it is about the weekend. It is really about trust: if a release can take production down and nobody can undo it in minutes, the calendar is only a symptom. The fix is a pipeline that makes every change small, tested and reversible.

      Build once, promote the same artifact

      Rebuilding per environment is how “works in staging” turns into an incident. Build a single immutable artifact, tag it with the commit SHA, and promote that exact image through staging and production. Only configuration changes between environments.

      name: ci
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm test -- --ci
      - run: docker build -t app:${{ github.sha }} .

      Pin base images and dependency versions, cache what is safe to cache, and keep the whole CI stage under ten minutes. A slow pipeline gets bypassed.

      Gate promotion with signals, not meetings

      A pipeline earns trust through automated checks that fail loudly:

      • Unit and integration tests on every push.
      • A smoke test against the freshly deployed environment before traffic shifts.
      • A canary that receives a small share of traffic while error rate and latency are compared with the stable version.
      • Automatic rollback when those comparisons breach a threshold.
      Measure it

      The four DORA metrics — deployment frequency, lead time for changes, change failure rate and time to restore service — tell you whether the pipeline is getting safer, not just faster.

      Separate deploy from release

      Feature flags let code reach production dark and be switched on gradually. Deploying becomes a routine, low-drama event, and releasing becomes a product decision you can reverse with a toggle.

      Make rollback boring

      Because every image tag is immutable, going back is a one-liner, and it should be rehearsed:

      kubectl rollout undo deployment/app
kubectl rollout status deployment/app

      If rolling back needs a ticket, a call or a hotfix branch, fix that before worrying about deploy frequency.
